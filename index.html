§ 00Premise

Why treat skills like a project at all?

An AI skill — a markdown file that teaches an agent how to do one specific job — has quietly become the unit of leverage in our work. A good one outlives the chat that produced it. A bad one rots into someone's private prompt drawer.

ThesisSkills are software. Manage them like software.

So we treat them the same way we treat any other shippable artifact: there is a backlog, there is a catalogue, there is an owner, there is a status, there is a repo, and where it makes sense, there is CI.

Two parallel systems already run on the same playbook inside Matrix. One is the squad's — our collective AI workflow. One is mine — a single manager's daily toolkit, sized for one person but built on the same shape. This document walks through both, then asks what the rest of the tribe would gain by adopting the model.

The point of the framing is boring on purpose: the same plumbing that makes engineering teams predictable should make AI work predictable too. Owner, status, deadline, paper trail. Nothing exotic — just portable.

Output contractEvery skill writes a structured Confluence page under Manager AI Assistant, mirrored to a local Obsidian vault.

Each specialist owns one analytical loop — sprint health, meeting follow-up, DR growth, idea hygiene — and publishes the result to the same Confluence parent page, on a predictable cadence. Smart-Todo doesn't redo their work; it reads them back. When sprint-daily flags a blocker on Monday morning, that blocker reappears in Tuesday's todo as [via sprint-daily] — already analysed, already prioritised.

The aggregation is what compounds: 30 minutes of cross-tool triage every morning compresses to a 10-second skim, and the analytical work itself isn't lost — it's a versioned page you can come back to.

All nine skills follow the same contract: a single SKILL.md that describes triggers, inputs, workflow, edge cases, and output format. Same author guide, same publish destination, same status flow. They're swap-replaceable.

§ 03The loop

Backlog → Catalogue. Auto-synced.

A skill's full life cycle moves through four stages. The transition between stages is mechanised — there is no manual page-shuffling between Confluence pages. The PM workflow, applied to AI skills.

Step 1
Drop into backlog

An idea lands in the AI Skills Backlog page on Confluence with owner, status, target repo. Same template every time.

Step 2
Build in repo

Implementation lands in .claude/skills or .codex/skills — code-related in carhire-homepage, otherwise matrix-skills.

Step 3
Status → ✅ Done

Owner flips status on the backlog row. PR merged. Skill is live.

Step 4
Auto-sync to catalogue

A GitHub Action (skills-docs-sync) detects the change, removes the row from backlog and writes the catalogue entry under the right phase.

§ 04Why it earns its keep

What this buys us.

Four outcomes I'd point to today. Skills are cheap to write. Managing them is what makes the investment compound — across one squad, or seven.

↳ Discoverability30s

Anyone in the squad can answer "do we have a skill for X?" in 30 seconds — one Confluence page, structured by phase.

↳ OnboardingDay 1

A new joiner reads the catalogue and is productive on day one. The skills are the team's externalised muscle memory.

↳ Compoundingn × ∞

A skill outlives any single chat or person. The investment in writing one pays back every time it runs — and the catalogue makes that runtime visible.

↳ Manager visibilityJQL-able

Status flow + owner field make AI work measurable — the same way Jira makes feature work measurable. No more invisible productivity.

§ 05What to copy

Four moves, borrowable.

Every manager runs differently. Every team carries a different load. But the shape of how skills get managed is portable. These four moves work on your personal toolkit (your Manager Skills) and on the squad's catalogue (your Team Skills) without modification.

A
Move 1 · Foundations

Treat skills like a project.

The mechanics that make features predictable — backlog · catalogue · owner · status · done — apply to skills without modification. The unit of work changes (a skill, not a ticket); the discipline doesn't. This is the move that makes everything else compound.

Avoid: keeping skills as private prompts in your head, in Notion, or buried in chat history.
B
Move 2 · Sequencing

Crystallise before you automate.

Phase 1: pin down what you already do, as a written skill — even if the only "automation" is you running it manually each day. Phase 2: only then add scheduling, cross-tool wiring, GitHub Actions. The unglamorous step is load-bearing — skipping it produces clever automation nobody uses.

Avoid: writing the GitHub Action before the SKILL.md exists.
C
Move 3 · Prioritisation

Let the pain pick the next skill.

Don't write skills speculatively. Watch where time actually leaks: PRs that keep doing the same fixup (harness gap?), Greenflag eating Tuesday afternoons, daily team ops that go fragile each sprint. The catalogue grows from observed friction, not from roadmap aspiration.

Avoid: building skills you think the team should want.
D
Move 4 · Compounding

Retro the system, not just the work.

At the end of every sprint, ask one question: "which moment this cycle would a skill have saved?" If a stage felt rough or one ate too much time, that's the prompt. Each retro produces 1–2 candidate skills for the next cycle. Run this for a quarter — the catalogue compounds, and so does the manager who keeps it.

Avoid: retros that only review tickets and never the toolchain.
The ask — let's run this model across the tribe. Once three or more squads keep catalogues on the same shape, we can see what's shipped vs. in progress across teams, and start sharing skills horizontally instead of rebuilding them three times.
